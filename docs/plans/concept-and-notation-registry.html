Plan · grammar · consumer: imas-codex S18

One definition per concept

The grammar says how a name is spelled. Nothing says how the shared ideas inside a name are defined. So the catalog writes the flux-surface average five ways and glosses the plasma boundary as the separatrix. This plan adds that missing layer beside the vocabularies it is keyed by, and releases it with them.

§1 — Why here, and why now

The imas-codex consistency census of 2026-10-12 (imas-codex:sn-catalog-consistency-census) measured 72 accepted entries re-deriving the flux-surface average, in five notations and with one wrong. 24 boundary entries call the plasma boundary the separatrix, and the WEST batch opens its documentation in four styles. The consumer plan imas-codex:sn-house-style authors a single house style to fix this. On 2026-10-12 the lead ruled that the house style lives in ISN now, released before the WEST re-cut, rather than in imas-codex first. A definition belongs with the grammar that names the thing defined, and every consumer of the standard should see it, not only the generator.

Existing guidance is the base, not a competitor. docs/guidelines.md states naming rules and the flux-surface-average tag. The shipped symbol definition policy requires every symbol to be defined by identity and name link. The locus registry already carries a definition per locus. The new layer adds what none of them hold: one canonical equation per concept, one symbol per quantity, and one opening template per name pattern.

Four existing owners are extended or referenced rather than restated. Per-token definitions live on the vocabulary entries (LocusEntry.definition, PhysicalBaseDef.definition, GeometryCarrierDef.definition in imas_standard_names/grammar/vocab_loaders.py). Alternate spellings live on their aliases and abbreviations. The writer's rubric (section order, the generic sign-convention form, equation and symbol rules) is entry_schema.fields.documentation.guidance in imas_standard_names/grammar/specification.yml, generated into field_schemas.py. The governed-term accessor is terms.py. imas-codex's cluster vocabulary (imas_codex/definitions/clusters/concepts.yaml) carries symbols for cluster labels; it is a consumer of this layer, recorded there rather than changed here.

§2 — The registry and its loader

Three files under imas_standard_names/grammar/vocabularies/conventions/:

  • concepts.yml — one entry per shared concept, keyed by the operator, locus, coordinate or base token that carries it. Each entry holds a canonical phrase, exactly one canonical LaTeX equation, its symbol table, forbidden variants as patterns, and whether a name using it restates the equation or only names the concept. It carries a one-sentence definition only for a token whose vocabulary entry has none (operators have none today). Where the token's entry already defines it, the accessor returns that definition, and a lead ruling that changes it is made on the token's own entry, so there is one definition per token.
  • notation.yml — one symbol per quantity or coordinate, keyed by base, subject, component or coordinate token, with its forbidden spellings. The loader refuses a forbidden spelling that equals one of the same token's registered aliases or abbreviations, so the two owners cannot disagree.
  • templates.yml — one description opening and one documentation opening per name pattern. A pattern key is written in grammar segments (a base and the segment kinds the name fills), so it is selected from the parse. The section order and the generic sign-convention form stay in specification.yml, and a template references them rather than restating them. Whether an entry carries a sign-convention paragraph depends on its COCOS transformation type, an entry field the parse does not yield, so that rule is not in the registry: the consumer decides it where the entry is known (imas-codex's documentation gates). Per-pattern openings are not added to specification.yml, whose guidance is the generic rubric every entry's schema carries.

The models and loaders go into imas_standard_names/grammar/vocab_loaders.py beside the existing ones, reusing _load_yaml and the registries it already loads. For concepts.yml and notation.yml, which are keyed by tokens, the loader refuses any key that is not a real token in the current vocabularies, so the registry cannot drift from the grammar. templates.yml is keyed by patterns, so its rule is that every token and segment kind a pattern names exists in the current grammar. The public accessor goes into imas_standard_names/grammar/terms.py beside fetch_standard_terms: it takes a parsed name and returns exactly the entries that apply to it. No new loader module is added. Surface: one accessor and one refusal family (an unknown token key, or a forbidden spelling that equals a registered alias) are added. Nothing is retired, because no per-token equation, per-quantity symbol or per-pattern opening exists to merge with.

Done when: the loader validates all three files and refuses one deliberately malformed entry per file, plus one entry keyed by a token that does not exist, each failing by name. For flux_surface_averaged_argon_density_at_plasma_boundary, the accessor returns the flux-surface-average concept, the plasma-boundary entry, the density notation and the species-density template, and nothing else.

§5 — Population, zone and aggregation tokens carry definitions

Three near-duplicate rulings carry a separating sentence (§7) that must render only on the names it describes. The registry cannot do that today. _vocabulary_definitions (imas_standard_names/grammar/vocab_loaders.py ~715) returns definitions only for locus, physical-base and geometry-carrier tokens. The population (populations.yml), zone (zones.yml) and aggregation (aggregations.yml) vocabularies are plain token lists, with any meaning in comments. The lead ruled on 2026-10-15 that the registry gains both mechanisms: definitions on these tokens (this section), and token conditions on templates (§6).

Each token in those three vocabularies may carry a definition, held in _vocabulary_definitions. Holding it is not enough. select_conventions (grammar/terms.py ~280) emits an applied definition only for a token keyed in concepts.yml, and uses the vocabulary text merely as fallback for such a key. So it must also emit an applied definition for a population, zone or aggregation token that carries one. AppliedConcept (terms.py ~116) requires phrase, equation and restates_equation, which a token definition does not have. Either make those fields optional for a definition-only entry, or add a sibling definition-only shape that renders beside concepts. Never invent a phrase or an equation to fill a required field. Say which you chose in the fragment. Change the files from lists to entries in the shape the locus registry and physical bases already use, so a token without a definition still loads. load_populations and load_aggregations return exactly the token sets they return today. load_zones returns exactly the same ordered tuple, because its order is the canonical intra-order rendering and validation rely on (vocab_loaders.py ~380). No consumer changes. Move the meanings now held in comments into definitions where a comment states one. Do not invent definitions for tokens whose meaning no comment records.

Done when:

  • a test shows load_populations and load_aggregations return the same token sets at base and at head, and load_zones the same ordered tuple;
  • _vocabulary_definitions returns a definition for a population, a zone and an aggregation token, and that definition appears in a rendered name carrying the token;
  • a token without a definition loads and contributes nothing;
  • each test fails with its mechanism removed, recorded with EXIT=;
  • the grammar, vocabulary and template tests pass at head, judged by delta against base.

§6 — A template may require or exclude tokens

select_conventions (imas_standard_names/grammar/terms.py ~297) selects a template from conventions/templates.yml by the name's base and the segment kinds present, through a subset test. So a template reaches every name of its pattern. A sentence about cold neutrals reaches electron_temperature, and a sentence about the unqualified triangularity reaches upper_triangularity_of_plasma_boundary.

A template entry may carry optional conditions:

  • required tokens per segment kind, for example population: [cold, hot] or aggregation: [total];
  • excluded segment kinds, for example a template for the unqualified quantity that excludes zone.

select_conventions applies the conditions after its subset test. An entry with no conditions selects exactly as it does today. A template entry may also carry an optional note: one sentence rendered after the documentation opening of every name that selects the entry. TemplateEntry (vocab_loaders.py ~662) has no field for such a sentence today, because its description and documentation are the pattern's openings. §7 places the separating sentences in notes. No precedence among templates exists today: they are an unordered list returned in file order (vocab_loaders.py ~678). Define how a conditioned entry and an unconditioned sibling combine or take precedence when both match, state the rule in the fragment, and test it.

Done when:

  • tests show a required-token condition admits only names carrying the token;
  • an excluded segment kind admits only names without it;
  • a note renders after the documentation opening on every name that selects its entry and on no other name;
  • every existing template selects as before, shown over the names the existing template tests render;
  • a test fixes the precedence rule: when a conditioned entry and an unconditioned sibling both match one name, the result is exactly what the stated rule says, and the test fails when the rule is reversed;
  • each test fails with its mechanism removed, recorded with EXIT=;
  • the grammar and template tests pass at head, judged by delta against base.

§7 — The sentences that keep near-duplicates apart

The coordinator ruled every near-duplicate overlap that touches the WEST roster as distinct (imas-codex docs/evidence/fragments/sn-catalog-grouping/scg-near-duplicate-rulings.json, 2026-10-13). Three of those rulings carry a template_sentence that separates two names which otherwise read alike. Use each sentence verbatim from that field:

  • cold or hot neutral temperature against neutral temperature;
  • unqualified triangularity against upper and lower triangularity;
  • total electron density against thermal and fast electron density.

After §5 and §6, place each sentence with the mechanisms those sections built: token definitions and conditioned template notes. The placement is the worker's to choose, and the done-when below is the contract. Two constraints are known. A token definition carries only what the token means in every name it fills, so a neutral-temperature sentence cannot go on cold, which also fills cold_electron_density. And a name can fill several segment kinds at once, as total_thermal_electron_density does, so a sentence placed in more than one entry must still render once per name. Say in the fragment where each sentence went and why.

Done when: a test renders the documentation of every name in each family that the graph-free registry can name:

  • temperature: electron_temperature, ion_temperature, neutral_temperature, and cold and hot neutral temperature;
  • density: electron_density and each population and aggregation form of it the registry composes;
  • triangularity: triangularity_of_plasma_boundary and its upper and lower forms.

The test asserts that each sentence appears exactly once on every name it describes, and on no other name in any of the three families, including names that fill more than one segment kind. It fails with any sentence removed, and fails when any sentence is duplicated so that some described name renders it twice. Both are recorded with EXIT=. For each sentence, a further control moves it to a placement that reaches a name it does not describe, and the test must then fail. Where no such placement exists for a sentence, say so in the fragment. The registry and template tests pass at head, judged by delta against base.

Render through one owner, not a test helper. Nothing in production yet reads AppliedTemplate.note. The only renderer is imas-codex, which inserts template.documentation alone (imas_codex/standard_names/workers.py ~9661 and imas_codex/standard_names/docs_gates.py ~983). Add one accessor beside select_conventions in imas_standard_names/grammar/terms.py. It returns, in order, the sentences that a name's selected templates contribute: each template's opening, then its note. The test asserts through that accessor. Switching the imas-codex writer and gate to it is a separate node in that repository. In tests/grammar/test_template_conditions.py, rename _legacy_selection and its docstring by what the oracle computes, a selection by the subset test alone with no conditions.
